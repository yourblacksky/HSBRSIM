# 酒馆战棋 AI 智能体开发规范 (Agent Development Specification)

## 1. 项目概述
本项目旨在构建一个用于《炉石传说》酒馆战棋模式的AI决策系统。核心目标是开发一个超人类水平的智能体，涵盖完整的对局模拟器、强化学习训练框架及发牌器元学习系统。
- **核心挑战**: 状态空间巨大 (≈10^12)，有限的可观察信息 (POMDP)，复杂的战斗随机结算。
- **核心策略**: "数据飞轮"——利用真实对局日志冷启动，通过自对弈生成海量数据，借助元学习适应发牌器的潜在动态。

## 2. 技术栈与选型规范
为避免兼容性问题并降低开发成本，AI开发必须严格遵循以下技术选型：

| 层级 | 规范选项 | 实施方案 | 强制等级 |
|:---|:---|:---|:---:|
| **语言** | Python（原型/编排）, C++/Rust（核心加速） | Python 3.10+ 作为主逻辑；性能热点迁移至 C++/pyrite (Rust) | High |
| **模拟器基础** | stone_ground_hearth_battles | Fork 作为起点，注意其已停止维护，需自建分支维护 | High |
| **卡牌数据** | HearthstoneJSON / hsdata | `pip install hearthstone_data`，零成本获取全量元数据 | **Critical** |
| **对局数据** | Power.log 解析 | 使用 python-hslog 自建管道；严禁依赖无公开 API 的商业数据库 | **Critical** |
| **强化学习** | PyTorch + PettingZoo + RLlib | stone_ground 原生支持，适配多智能体回合制环境 | High |
| **接口标准** | PettingZoo AEC (Agent Environment Cycle) | 必须封装为标准 PettingZoo 接口以便训练 | High |

## 3. 核心架构蓝图
采用五层架构设计。AI在处理项目代码时，应始终区分这五层边界：

1.  **数据获取层 (Data Layer)**: 负责 `HearthstoneJSON` 静态数据、`Power.log` 动态轨迹的获取与解析。
2.  **规则引擎层 (Rules Engine)**: 定义游戏规则（随从池、三连、战斗结算），须独立于模拟器，确保状态一致性。
3.  **模拟器核心层 (Simulator Core)**: 提供环境接口，必须支持高速并行采样（目标 >10,000 steps/sec）。
4.  **训练层 (RL Training)**: 包含模仿学习(SL)、PPO、League种群训练和发牌器元学习。
5.  **服务层 (Serving)**: 模型推理与决策建议接口。

## 4. 关键开发原则与约定

### 4.1 运行时性能优先
- **硬性指标**: 不应将 Python 视为最终性能方案。模拟器必须预留 C++/Rust 绑定接口。
- **瓶颈认知**: CPU是经验生成的瓶颈，非GPU。请参照报告计算加速比差异（500 steps/秒 vs 50,000 steps/秒）。
- **优化路径**: Python热点函数 -> Cython/Numba -> PyO3/Rust绑定 -> EnvPool并行。

### 4.2 严格的规则一致性
- **随从池事务性**: 购买/出售/淘汰必须通过事务性操作更新全局共享池。严禁出现并发导致的副本数错误。
- **战斗结算**: 必须实现代际队列 (Generation Queue) 处理死亡结算顺序，确保圣盾/剧毒/复生的互交完全准确。
- **Ban/发现**: 种族Ban逻辑需用 OR 条件过滤双种族随从；Discover 效果的卡牌来源必须是随从池。

### 4.3 数据闭环原则
- **冷启动**: 没有公开数据集是核心瓶颈。必须优先实现 `Power.log -> 解析器` 管道以获取种子数据（约10K局）。
- **无需等待官方**: 不依赖 Blizzard API 提供动态对局数据，一切以社区数据源和自对弈为准。

## 5. 分阶段实施目标 (12个月路线图)

### Phase 1: 基础验证 (M1-M3)
**目标: 跑通数据飞轮最小闭环。**
- **任务**: 搭建 python-hslog 解析器；验证规则引擎随从池操作；在 stone_ground 上运行无英雄版对局。
- **产出**: 准确率 >95% 的日志解析器；一个能执行标准对局的模拟环境。

### Phase 2: 加速与冷启动 (M4-M6)
**目标: 解决性能瓶颈并实现冷启动训练。**
- **任务**:
    1.  **核心加速**: 将战斗结算迁移至 C++/Rust 核心，实现 50x 性能提升。
    2.  **模仿学习**: 用解析的真实对局训练初始策略（行为克隆）。
    3.  **发牌器统计**: 基于真实数据训练数据驱动发牌器。
- **产出**: 单步耗时 <0.1ms 的战斗引擎；胜率 >50% 的初始AI模型。

### Phase 3: Meta-RL与系统化 (M7-M12)
**目标: 应对隐藏参数并实现泛化。**
- **任务**:
    1.  **HiP-POMDP**: 实施 MB-MPO 框架，让策略网络学习在局内推断发牌器“个性”。
    2.  **League训练**: 引入 PFSP (优先虚拟自对弈) 防止策略退化。
    3.  **服务化**: 封装为低延迟 (<500ms) 的决策微服务。
- **产出**: 具备自适应能力的最终智能体；可扩展的训练集群。

## 6. AI 交互注意事项

1.  **引用源**: 讨论算法或数据时，务必引用调研报告中的来源 ID（如 ^7^, ^29^）。
2.  **博弈论视角**: 时刻考虑酒馆战棋的8人非合作博弈特性。在训练中注意非传递性（动态平衡而不只是绝对强度）。
3.  **发牌器独立建模**: 不要假设发牌器是均匀的。建议默认加载上下文编码器检测历史发牌痕迹。
4.  **合规边界**: 建议的插件功能（插件层）仅限于读取日志并提供显示覆盖 (Overlay)，不能自动执行游戏操作。
